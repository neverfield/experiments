# Run the Docker pytest from a standalone clone, not a git worktree

**Experiment:** repo-discovery · **Added:** 2026-11-09 · **Source:** branch `cursor/dev-shortcut-checks-e803` (`repo-discovery/docker/run.sh`, `src/repo_discovery/split.py`), reproduced at `b135d1f`

**What happened.** On the Mac, the main checkout already carries git worktrees (the scoring-freeze ones), and another worktree is the quick way to test a PR's commit without touching the checkout a running queue reads. `docker/run.sh` mounts the checkout's root at `/work`. In a worktree, `.git` is a one-line file, `gitdir: <host path>/.git/worktrees/<name>`, and that host path doesn't exist in the container, so every git command under `/work` fails with `fatal: not a git repository`. At `b135d1f` the suite run from a worktree gave 1 failed and 425 passed: `test_scratch_home_fails_plugin_fetches_without_the_network` runs `git ls-remote` in its working directory and expects git to fail on the redirected URL, and git failed on the missing repository instead. The same commit from a standalone clone gave 426 passed and 1 skipped. `check_registered` also runs git in the checkout (`split.py`, the parent of `repo-discovery/`), so a test-split run from a worktree inside the runner stops the same way.

**What it cost.** Here about a minute, because the worktree run was a deliberate check. Unplanned, it fails the merge rule (the full suite must pass in the Docker runner first), and the failing test reads as a regression in the plugin-fetch guard rather than a property of the checkout.

**Next time.** Run `docker/run.sh pytest` from a standalone clone (`git clone`, or `git clone <bundle>` for a handoff), detached at the commit under test, and keep worktrees for host-side work. Leave the container's network on for that run: the image's entrypoint pip-installs the package first, and with `--network none` it fails on `hatchling` before any test runs. Point `RD_VOLUME` at an empty volume so the tests never see `rd-data`.
